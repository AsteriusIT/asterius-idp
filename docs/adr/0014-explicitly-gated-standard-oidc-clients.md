# ADR-0014: Standard OIDC clients are explicit tenant and application opt-ins

- **Status:** Accepted
- **Date:** 2026-09-19
- **Bead:** ast-dng9
- **Supersedes:** ADR-0002's decision that FAPI is the only client mode
- **Deciders:** Quentin RODIC

## Context

ADR-0002 made FAPI 2.0 the only supported client profile. That gives a strong
default but prevents migration of conventional confidential OIDC applications
whose libraries support `client_secret_basic` and authorization-code flow but
not PAR or asymmetric client authentication.

A tenant-wide compatibility mode would silently weaken every application. An
inferred mode (for example, treating the presence of a secret as non-FAPI)
would make the effective security contract difficult to inspect and could turn
a credential edit into a profile downgrade.

## Decision

FAPI remains the default for existing and new clients. Standard OIDC is
available only when both controls agree:

1. the tenant setting `allow_non_fapi_clients` is true; and
2. the application's `compliance_profile` is explicitly `oidc`.

Dynamic client registration remains FAPI-only. The administrative API is the
only path that can select `oidc`, after checking the tenant permission. API and
console documents always render the effective profile. Only `fapi` clients are
shown with a FAPI badge.

The initial OIDC profile has exactly two FAPI exemptions:

- a direct authorization-code request may be sent to `/authorize` without
  first using PAR; and
- the confidential client may authenticate with `client_secret_basic`.

Everything else remains on the hardened shared path: exact HTTPS redirect URI
matching, response type `code`, PKCE `S256`, sender-constrained access tokens,
the signing-algorithm allow-list, bounded single-use authorization codes, and
the same consent, resource, RAR, request-object and grant validation. In
particular, this decision adds neither public clients, bearer access tokens,
`client_secret_post`, implicit/hybrid flows, ROPC nor relaxed redirects.

Client secrets are 256 random bits generated by the server. Plaintext is
returned only by creation or explicit rotation, with `no-store`; PostgreSQL
holds only a SHA-256 digest. Authentication compares fixed-size digests in
constant time. Rotation replaces the digest atomically, and revocation clears
it atomically. The registration document never accepts administrator-chosen
secret material and a read never returns a secret.

## Consequences

Tenants can migrate conventional server-side OIDC applications without
weakening FAPI clients. The effective profile is queryable rather than inferred,
and disabling the tenant permission blocks new profile selection and direct
authorization entry.

A standard OIDC client does not satisfy the FAPI 2.0 Security Profile and must
not be represented as such. Tenant operators now own an explicit compatibility
decision, and conformance claims apply to clients whose effective profile is
`fapi`, not to every client hosted by the deployment.

The implementation has two protocol branches to test. The shared authorization
validator deliberately remains single: direct requests are validated and
stored as an internal authorization request before entering the existing
interaction pipeline.

## Rejected alternatives

- **Tenant-wide downgrade:** too broad; one migration would weaken unrelated
  clients.
- **Infer the profile from `client_secret`:** makes mode changes implicit and
  creates ambiguous records.
- **Accept `client_secret_post`:** places a reusable credential in request
  bodies and expands the authentication surface without a migration need.
- **Relax PKCE, redirect matching or sender constraint:** none is required for
  conventional confidential-client interoperability, so none is exempted.
