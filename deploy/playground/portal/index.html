Two apps, one sign-in

Compare separate app sessions backed by the same identity provider.

Open Demo AOpen Demo B
  1. Sign in to Demo A, then open Demo B in the same browser.
  2. Compare the subject and claims displayed by each app. Consent may still be required for the second app.
  3. Refresh tokens, check the IdP session or force reauthentication using the app’s controls.
What should happen?

The existing IdP session can satisfy the second sign-in when policy allows. Each application keeps its own session. Pairwise subjects may differ; that is expected when their sectors differ.

Use Revoke and log out to finish. Local logout is not proof that every unrelated application session has ended.

A protected financial API

A browser app uses a confidential backend to access an exact resource audience.

Open Financial
  1. Open Accounts while signed out: the application should ask you to sign in.
  2. Sign in with Asterius, then load the sample checking and savings accounts.
  3. Submit a small sample transfer, inspect the response and sign out.
What should happen?

A valid authorized session can read accounts and perform an allowed sample transfer. Missing authorization must not return protected account data. A rejected transfer must leave sample balances unchanged.

Sample state is local to this service and resets on restart. No bank or external payment system is connected.

Try a protocol journey

Use the protocol lab to test the journeys implemented there and inspect actual outcomes.

Open protocol lab
  1. Start device authorization, or enter the disposable user’s login hint to start CIBA.
  2. Follow the displayed device link, or open My account approvals for CIBA; approve or deny the request.
  3. Poll at the displayed interval, inspect UserInfo and introspection, then revoke and check that the token is inactive.
What should happen?

A successful request must fit the registered client, resource and current policy. Missing configuration or a refused request is shown as an outcome, rather than a fabricated successful token.

This lab implements device and CIBA approval, polling, UserInfo, introspection and revocation. Machine grants and token exchange are separate setup-dependent exercises. A globally enabled protocol does not automatically configure an external peer.

Explore further with the right fixture

The full local feature tour contains 98 proposed scenarios. This playground supplies the applications above and a namespace-local read-only Kubernetes fixture. It does not present unconfigured integrations as working demos.

Ready for browser exploration
Console navigation, people, groups, roles, policy inspection, architecture drafts, preferences, branding preview and application health. Writes require the corresponding permissions.
Needs explicit configuration
Temporary privileges, access reviews, conditional access, token exchange, grant management, request signing and device-aware enforcement need their own client, policy and assurance setup.
Needs a separate peer or device
OIDC providers, SAML, SSF delivery, SCIM receivers, LDAP, federation, claims providers, wallets, workload issuers, passkeys and authenticators.
Needs a separate deployment decision
mTLS, AuthZEN and self-registration are currently disabled. Full native Entra provisioning remains a separate future cloud exercise. Nothing here starts a cloud provisioning job.
